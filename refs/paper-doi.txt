Abstract
Large Language Models (LLMs) are increasingly embedded into
software systems, yet most current solutions are either LLM-based,
wrapping an existing system around an LLM, or LLM-augmented,
embedding LLMs into existing workflows. These approaches yield
quick gains but remain brittle, difficult to reproduce, and poorly gov-
erned. We introduce the notion ofLLM-native applications: systems
conceived from the outset with an LLM as the orchestration core, co-
ordinating tools, memory, knowledge integration, and governance.
We present a reference architecture and illustrate feasibility through
an LLM-native copilot for literature reviews. We further propose a
lifecycle model that highlights how development processes change
when LLMs become first-class orchestrators.

Motivation. LLM models are usually integrated in software
through systems that serves and exposes API’s. This type of model
management has favoured two main approaches: LLM-based ap-
plications, which exposes the model as the main engine, such as
chatbots or summarizers, and LLM-augmented applications, which
embed an LLM as a peripheral service that enhances existing work-
flows, as in IDEs or retrieval-augmented assistants [8]. While im-
pactful, both approaches may introduce Architectural Technical
Debt (ATD) [3] due to incremental design [7]. Architectural reflec-
tions increasingly call for principled approaches to design LLM-
enabled systems that go beyond local integration [1].
Problem. Therefore, an architectural model that favours the
design from the ground up with the LLM as the organizing principle
is missing. Without clear definition, reference architecture, and
development lifecycle, LLMs are underutilized as “add-ons” for
classic architectures. This gap is particularly pressing given the
rising complexity of tasks delegated to LLMs and the governance,
reproducibility, and adaptability challenges they entail [1].
Our Approach. We introduce the concept of LLM-native appli-
cations, which represent a paradigm shift: they are conceived from
day one around the model’s reasoning, memory, governance, knowl-
edge integration, and orchestration capabilities, requiring funda-
mentally different architectural thinking, since they are treated now
as first-class concerns.
2 The Use of LLMs in Software Development
We distinguish three modes LLM-enabled systems, each reflecting
a different architectural stance.
LLM-based applications. These systems directly expose the
capabilities of an LLM, often via APIs, without substantial addi-
tional logic. ChatGPT and Gemini are good exemplars. While highly
accessible, their architecture tends to be shallow, often limited to
simple prompt–response loops.
LLM-augmented applications. These are applications that in-
corporate LLMs as a peripheral service to enhance existing function-
ality. At design time, the model supplements the development of the
software itself but does not orchestrate its architecture. Examples
include GitHub Copilot suggesting code within IDEs or assistants

LLM-native applications. Distinct from the incrementalism
of the first two categories, LLM-native applications are conceived
from the outset with the LLM at the centre of the architecture. The
LLM acts as the orchestrator: it interprets user intent, generates
and executes plans, invokes external tools, integrates knowledge,
manages memory, and enforces governance. Other components
exist to serve this orchestration, not merely to wrap or extend it.
3 Reference Architecture
A general representation of the architecture can be seen in Figure 1.
The main layers and components are described as follows.
User Interface (UI). Users interact via text, voice, or multi-
modal inputs, managing intermediate plans, retrieved evidence,
and governance warnings.
LLM Core. The central organizer interprets intent, decomposes
tasks, reasons over alternatives, and orchestrates component in-
teractions. The Core produces a plan that structures tool calls and
knowledge access; plans are human-inspectable and versioned for
replay. Unlike augmentation, the Core governs reasoning and exe-
cution flow, consolidating accountability in a single locus of control.
Governance & Safety Layer.Governance validates plans against
policies such as privacy constraints, requirements, and bias checks.
Application Orchestration. Orchestrator invokes tools, sched-
ules calls, manages retries, and results. Failures trigger bounded
retries and re-planning by the Core, favouring resilience.
Knowledge Base (KB). Retrieval pipelines (e.g., RAG [5]) fetch
relevant documents from structured and unstructured sources, sup-
plying evidence for reasoning.
Tool & Service Layer. Specialized tasks (e.g., PDF parsing, code
execution, data cleaning) are delegated to external services via
typed interfaces. The Core invokes them and integrates structured
results. Function calling and self-instructed tool use ensure schema
validation, bounded retries, and sandboxed execution [6].
Context & Memory Manager. Manages context and persistent,
versioned memory to ensure continuity and reproducibility.
The execution goes as: (1) the user submits a request via UI; (2)
the Core interprets it and proposes a plan; (3) governance validates
the plan against policies; (4) orchestration executes tool and KB
calls; (5) Core reconciles results into outputs; (6) governance per-
forms post-execution validation and (7) the UI delivers the output,
and the relevant context is persisted in memory.
LLM-native lifecycles adopt an LLM-first stance from day one:
the LLM Core orchestrates plans, tools, memory, retrieval, and gov-
ernance, which forces process changes across requirements, design,
implementation, testing, deployment, and evolution. Table 1 high-
lights the differences between types of LLM-enabled applications.
To illustrate feasibility, we developed SCRIBE 1, an LLM-native
copilot for systematic literature reviews. Researchers submit queries
such as “Summarize recent approaches to LLMs in software testing” .
The LLM Core interprets the request, generates a plan, and orches-
trates retrieval, filtering, and synthesis under governance checks
before producing a structured report with citations.
